Check your log format first

The agent raises incidents only for lines it can read. Each error line must use one of these formats:

FormatExample line
Bracketed[2026-10-27T10:00:00Z] [ERROR] [orders-api] DatabaseTimeout: connection refused
JSON lines (e.g. winston){"level":"error","message":"PaymentFailed: gateway 502","service":"orders-api","timestamp":"2026-10-27T10:00:05Z"}
Node logger style2026-10-27 10:00:01:184 [error] Error fetching report metrics: fetch failed
  • ERROR, FATAL, CRITICAL become high severity; WARN becomes medium. INFO and DEBUG are ignored.
  • Raw stack traces never raise an incident on their own. They are attached as context when a proper error line fires.
  • JSON loggers must write level as text ("error"). Pino's numeric levels ("level":50) are not recognised; configure pino to print labels.
  • pm2 users: the pm2 logs error file holds whatever your app prints. If it uses plain console.error, switch to a structured logger (winston JSON is easiest) or the bracketed format.

Verify the install

sre-agent version                     # sre-agent 2.0.0
id sre-agent                          # the service user exists

The install put the program in /opt/sre-agent, created the sre-agent system user, wrote the config file with a unique API key and approval secret for this server, and registered the sre-agent systemd service (enabled, not started).

3Let the agent read your log file

Same-server logs only. Skip this step if the log is on another server (SSH). The agent runs as the sre-agent user, which must be able to read the log file and open its folders.

Logs under /var/log/... (most common)

sudo apt install -y acl
sudo setfacl -m u:sre-agent:rx /var/log/orders-api                 # open the folder
sudo setfacl -m u:sre-agent:r /var/log/orders-api/error.log        # read the file
sudo setfacl -d -m u:sre-agent:r /var/log/orders-api               # new/rotated files too
sudo -u sre-agent head -1 /var/log/orders-api/error.log            # must print a line, not "Permission denied"

pm2 logs under a home folder

For example /home/deploy/.pm2/logs/orders-api-error.log:

sudo apt install -y acl
sudo setfacl -m u:sre-agent:x /home/deploy /home/deploy/.pm2       # pass through only
sudo setfacl -m u:sre-agent:rx /home/deploy/.pm2/logs
sudo setfacl -m u:sre-agent:r /home/deploy/.pm2/logs/orders-api-error.log
sudo setfacl -d -m u:sre-agent:r /home/deploy/.pm2/logs
sudo -u sre-agent head -1 /home/deploy/.pm2/logs/orders-api-error.log

If you run the agent with systemd and the log is under /home, let the service see /home (it hides home folders by default):

sudo systemctl edit sre-agent

Add these lines in the editor, then save:

[Service]
ProtectHome=read-only

For SSH, the setup then asks three more things:

  • Create one for the agent now? [Y/n]: press Enter. It prints a public key starting ssh-ed25519 .... Copy it.
  • Connect to 10.0.1.25:22 now to trust its host key? [Y/n]: press Enter.
  • Does the fingerprint match? [y/N]: on the log server run for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf $f; done and compare the SHA256:... of the same key type. Type y only if they match.

Then, on the log server, allow that key to log in:

sudo -u logreader mkdir -p ~logreader/.ssh
echo 'ssh-ed25519 AAAA... sre-agent@ops-server' | sudo -u logreader tee -a ~logreader/.ssh/authorized_keys
sudo chmod 700 ~logreader/.ssh && sudo chmod 600 ~logreader/.ssh/authorized_keys

5Start it

5A · With systemd

sudo systemctl start sre-agent          # skip if setup already started it
sudo systemctl status sre-agent         # Active: active (running)

It starts automatically at boot (the package enabled it).

5B · With pm2

pm2 must run the agent as root; the agent then switches itself to the sre-agent user. This is root's own pm2 list, separate from your app user's list.

sudo systemctl disable --now sre-agent                                   # make sure systemd does not run it too
sudo pm2 start /usr/bin/sre-agent --name sre-agent --interpreter none -- serve
sudo pm2 save                                                            # remember it
sudo pm2 startup systemd                                                 # start root's pm2 at boot (once per server)
sudo pm2 list                                                            # sre-agent  online

If sudo pm2 says “command not found” (pm2 installed with nvm), pass your PATH. Do the same for save, startup and list:

sudo env "PATH=$PATH" pm2 start /usr/bin/sre-agent --name sre-agent --interpreter none -- serve

6Verify everything works

Run these in order. Each comment says what you should see.

# 1. Health check: all required checks OK
sudo sre-agent doctor

# 2. Process is running as the sre-agent user
ps -o user=,cmd= -C python3 | grep sre_agent      # sre-agent  ... -m sre_agent serve

# 3. Web API answers
curl -s localhost:8000/health                      # {"ok":true,"version":"2.0.0",...}

# 4. API is protected
curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/issues                              # 401
KEY=$(sudo sed -n 's/^SRE_API_KEY=\([^ ]*\).*/\1/p' /etc/sre-agent/sre-agent.env)
curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: $KEY" localhost:8000/issues         # 200

# 5. The watcher started
sudo grep -m1 "auto mode ON" /var/log/sre-agent/sre.log          # a line with "auto.01.start"

End-to-end test: make a test incident

Write one test error line into the watched log (for SSH, run it on the log server). Use your service name and log path:

echo "[$(date -u +%Y-%m-%dT%H:%M:%SZ)] [ERROR] [orders-api] SreAgentTest: this is a test error, please ignore" \
  | sudo tee -a /var/log/orders-api/error.log

Within a few seconds:

curl -s -H "X-API-Key: $KEY" localhost:8000/issues | head -c 400
# {"issues":[{"id":"...","service":"orders-api","error":"SreAgentTest","severity":"HIGH","state":"open","count":1,...

An incident card arrives in Slack / Google Chat / email with the root-cause summary and Approve / Reject / Request changes buttons. Click Reject for the test. If the issue appears but no message arrives, see Troubleshooting.
