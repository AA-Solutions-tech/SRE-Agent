SRE Agent 1.2.0: deployment guide

Install the agent from the GitHub release, set it up with questions, and check that it works. AA Solutions package set.

Release page: github.com/AA-Solutions-tech/SRE-Agent/releases/tag/v1.2.0 · Time needed: about 20 minutes

Overview

The agent watches your application logs, groups the errors into issues, finds the likely cause, proposes a code fix and opens a pull request. A person approves each step with a button in Slack, Google Chat or email. The agent only makes outbound connections (AI service, Slack, GitHub). It needs no inbound port, unless you want people to click Approve links in a browser.

1. Downloadfiles from the release page
2. Installpackage, tarball or Docker
3. Logslet the agent read them
4. Setupanswer the questions
5. Startand run the health check
6. Testone test error
No console is needed.You get everything from the GitHub release page. You set the agent up with sre-agent setup. A hosted console is optional (see the end of this guide).

3Download and check the files

Open the release page and download the file for your host, and SHA256SUMS. Or use the command line:

VERSION=1.2.0
BASE=https://github.com/AA-Solutions-tech/SRE-Agent/releases/download/v$VERSION

# Example for Ubuntu / Debian on an amd64 CPU:
wget $BASE/sre-agent_$VERSION-1_amd64.deb
wget $BASE/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS      # expect: sre-agent_1.2.0-1_amd64.deb: OK
If the check does not say OK, stop.Download the file again. Do not install a file that fails the check.

4Install

Ubuntu / Debian (.deb)

sudo apt install ./sre-agent_$VERSION-1_amd64.deb

RHEL / Rocky / Alma / Amazon Linux (.rpm)

sudo dnf install ./sre-agent-$VERSION-1.x86_64.rpm

On ARM servers use _arm64.deb or .aarch64.rpm.

After a package install you see a message that ends with the next step. The service is enabled but not started. The install did these things: put the program in /opt/sre-agent, made the sre-agent system user, wrote /etc/sre-agent/sre-agent.env with a unique API key and approval secret for this server, and registered the sre-agent systemd service.

sre-agent version                      # sre-agent 1.2.0
sudo ls -l /etc/sre-agent/             # sre-agent.env

Portable tarball (any Linux with systemd)

tar xzf sre-agent-$VERSION-linux-amd64.tar.gz
cd sre-agent-$VERSION-linux-amd64
sudo ./install.sh

It gives the same result as the package. The host needs git (for code fixes). The installer refuses a tarball for the wrong CPU.

Docker

  1. Load the image: 
    docker load -i sre-agent-image-$VERSION-amd64.tar.gz
    The image is named sre-agent-aa:1.2.0-amd64 (or -arm64).
  2. Make a folder. Save the file below as compose.yaml in it. Make a file .env in the same folder with one line: 
    SRE_AGENT_IMAGE=sre-agent-aa
SRE_AGENT_VERSION=1.2.0-amd64
  3. Answer the setup questions. The answers are saved in the data volume: 
    docker compose run --rm sre-agent setup
  4. Start it: 
    docker compose up -d
  5. Check it: 
    docker compose logs -f
docker compose exec sre-agent sre-agent doctor

compose.yaml:

name: sre-agent
services:
  sre-agent:
    image: ${SRE_AGENT_IMAGE:-sre-agent-aa}:${SRE_AGENT_VERSION:-latest}
    env_file: [.env]
    restart: unless-stopped
    init: true
    stop_grace_period: 30s
    read_only: true
    tmpfs: ["/tmp:size=256m,mode=1777"]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    pids_limit: 512
    volumes:
      - sre-data:/var/lib/sre-agent
      # Logs of your app, read-only. In setup use the path inside the container, e.g. /logs/myapp/error.log
      # - /var/log/myapp:/logs/myapp:ro
volumes:
  sre-data:
Rules for Docker
  • One container, one volume. The database has one writer. Never run two copies on the same volume.
  • The container runs as user 10001 with a read-only root file system, no extra rights and no-new-privileges.
  • Do not mount the Docker socket into the agent. It gives root on the host. journald: sources are not available in the container.
  • The image has no Node or Python tools for your tests. The agent opens the pull request and your CI runs the tests.

5Let the agent read the logs

First check the log format

The agent raises an incident only for lines it can read. Each error line must be in one of these formats:

FormatExample line
Bracketed[2026-10-27T10:00:00Z] [ERROR] [orders-api] DatabaseTimeout: connection refused
JSON lines (for example winston){"level":"error","message":"PaymentFailed: gateway 502","service":"orders-api","timestamp":"2026-10-27T10:00:05Z"}
Node logger style2026-10-27 10:00:01:184 [error] Error fetching report metrics: fetch failed
Python logging2026-11-11 10:44:33,351 WARNING psa_ai.llm model call failed: timeout
uvicorn / gunicornERROR: [Errno 98] Address already in use
loguru / Flask2026-11-11 10:44:33.351 | WARNING | app.main:handler:42 - slow query
  • ERROR, FATAL, CRITICAL are high severity. WARN is medium. INFO and DEBUG are ignored.
  • A raw stack trace line alone never raises an incident. It is attached as context to a proper error line.
  • JSON loggers must write level as text ("error"). Pino numeric levels (50) are not read. Configure pino to print level labels.
  • A pm2 time stamp in front of a line (time: true) is fine. It is ignored.

Log files on this server

The agent runs as the sre-agent user. This user must be able to read the file and open its folders. (Docker: mount the folder read-only instead, see above.)

sudo apt install -y acl                                        # RHEL: sudo dnf install -y acl
sudo setfacl -m u:sre-agent:rx /var/log/orders-api              # open the folder
sudo setfacl -m u:sre-agent:r  /var/log/orders-api/error.log    # read the file
sudo setfacl -d -m u:sre-agent:r /var/log/orders-api            # new and rotated files too
sudo -u sre-agent head -1 /var/log/orders-api/error.log         # must print a line, not "Permission denied"

Apps that run under pm2

Install the agent on the same host as the apps. systemd runs the agent. pm2 keeps your apps. Do not run the agent under pm2 as well.

  1. pm2 writes each app log to ~/.pm2/logs/<app>-error.log (for example /home/deploy/.pm2/logs/orders-error.log). Give the agent access: 
    sudo apt install -y acl
sudo setfacl -m u:sre-agent:x /home/deploy /home/deploy/.pm2        # pass through only
sudo setfacl -m u:sre-agent:rx /home/deploy/.pm2/logs
sudo setfacl -m u:sre-agent:r /home/deploy/.pm2/logs/orders-error.log
sudo setfacl -d -m u:sre-agent:r /home/deploy/.pm2/logs
sudo -u sre-agent head -1 /home/deploy/.pm2/logs/orders-error.log
  2. systemd hides /home from the service. Allow it to see /home: 
    sudo systemctl edit sre-agent
    Add these lines in the editor, then save: 
    [Service]
ProtectHome=read-only
  3. In the setup, name each app after an @: 
    /home/deploy/.pm2/logs/orders-error.log@orders,/home/deploy/.pm2/logs/billing-error.log@billing
The pm2 error file holds whatever the app prints to stderr.If your app uses console.error for normal messages, switch to a structured logger (winston JSON is the easiest) or use the bracketed format.

Apps that run in Docker

Choose one way for each app:

WayWhenHow
Log folder (best)The app can write a log file.Mount a host folder into the app container, for example -v /var/log/myapp:/app/logs. A package agent on the host reads /var/log/myapp/error.log as a normal file (see "Log files on this server"). Or mount the folder read-only into the agent container.
docker:<container>Only if you accept the risk.The package agent runs docker logs. This needs Docker access for the sre-agent user, which is root-equivalent on that host.
Error toolThe app writes only to stdout.Use Sentry, Datadog, New Relic, Application Insights or CloudWatch (a connector reads the errors), or send errors to the signed /ingest route.

Logs on another server (SSH)

The setup can make an SSH key for the agent and trust the server's host key. You do these two things on the log server when the setup asks:

  1. The setup prints a public key (starts with ssh-ed25519). Add it to the log user: 
    sudo -u logreader mkdir -p ~logreader/.ssh
echo 'ssh-ed25519 AAAA... sre-agent@ops-server' | sudo -u logreader tee -a ~logreader/.ssh/authorized_keys
sudo chmod 700 ~logreader/.ssh && sudo chmod 600 ~logreader/.ssh/authorized_keys
  2. The setup shows the server's host key fingerprint. Compare it with the real one on the log server. Answer y only if they are the same: 
    for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf $f; done

A read-only user is enough. The agent never trusts a host key by itself.

6Run the setup

sudo sre-agent setup                  # package or tarball
docker compose run --rm sre-agent setup    # Docker

The command asks questions, one section at a time, and saves the answers in /etc/sre-agent/sre-agent.env (Docker: /var/lib/sre-agent/sre-agent.env in the data volume). It makes APPROVAL_SECRET and SRE_API_KEY for you.

Keys to pressWhat it does
EnterKeep the value in [brackets], or skip an optional question.
-Clear an optional value.
Ctrl+CQuit and save nothing.
SectionWhat it asksRequired
llmProvider, API key (typed hidden), model. Leave the model empty for the provider default.Yes
notificationsChannels: Slack, Google Chat, email. Slack webhook; optional bot token and app token for buttons inside Slack. SMTP details for email (Gmail needs an app password).At least one channel
approversSlack member ids and names of the people who may press Approve. Find an id in Slack: profile > More > Copy member ID. Web, email and Google Chat links never count as verified.Recommended
logsA log file on this server, or on another server over SSH. Service name (short, no spaces). Several sources: /var/log/a/error.log@a,/var/log/b/error.log@b.Yes
webPublic URL for Approve links, listen address, port. Keep 127.0.0.1 and put nginx or Caddy with HTTPS in front. A localhost URL does not work for links in Slack or email.Defaults offered
ticketsJira site, account email, API token, project key. Adds an "Add to Jira" button.Optional
codeRepository clone path, base branch, test and lint commands, GitHub token. The token needs Contents and Pull requests read/write on that repository.Optional
automationWatch the logs by itself, coding agent, push to remote, ship mode. Leave all of them off at first.Optional
advancedSlack channel id (one thread per incident), time zone, Jira project map and statuses, report repos, seconds between log reads, SSH host key check.Optional

At the end the command shows a summary, saves (it keeps a .bak copy), runs sre-agent doctor and offers to start the service.

Change one section later: sudo sre-agent setup --only notifications. Section names: llm, notifications, approvers, logs, web, tickets, code, automation, advanced.

Ship mode is approve by default.The agent always asks a person before it commits, pushes or opens a pull request. It holds high-risk changes for approval in every mode. Turn on the coding agent only when the incident cards look right.

7Start it and check it

sudo systemctl restart sre-agent       # package or tarball
sudo systemctl status sre-agent        # Active: active (running)
docker compose up -d                   # Docker

The service starts at boot (the package enabled it). Run these checks in order:

# 1. Health check. Every required line must be OK.
sudo sre-agent doctor

# 2. The web API answers
curl -s localhost:8000/health                    # {"ok":true,"version":"1.2.0",...}

# 3. The API is protected
curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/issues                            # 401
KEY=$(sudo sed -n 's/^SRE_API_KEY=\([^ ]*\).*/\1/p' /etc/sre-agent/sre-agent.env)
curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: $KEY" localhost:8000/issues       # 200

# 4. The watcher started
sudo grep -m1 "auto mode ON" /var/log/sre-agent/sre.log

In Docker, run the first command as docker compose exec sre-agent sre-agent doctor.

A line marked FAIL must be fixed.A WARN is fine for settings you do not use yet (for example TEST_CMD while code fixes are off). Read every WARN.

8Test with one error

Write one test error line into the watched log. Use your service name and path. For an SSH source, run it on the log server.

echo "[$(date -u +%Y-%m-%dT%H:%M:%SZ)] [ERROR] [orders-api] SreAgentTest: this is a test error, please ignore" \
  | sudo tee -a /var/log/orders-api/error.log

Within a few seconds:

curl -s -H "X-API-Key: $KEY" localhost:8000/issues | head -c 400
# {"issues":[{"id":"...","service":"orders-api","error":"SreAgentTest","severity":"HIGH","state":"open","count":1,...

An incident card arrives in Slack, Google Chat or email with the cause and the Approve, Reject and Request changes buttons. Click Reject for the test.

Checklist

  • sre-agent doctor shows all required checks passed
  • /health returns "ok":true
  • /issues returns 401 without the key and 200 with it
  • auto mode ON is in /var/log/sre-agent/sre.log
  • The test error became an issue and a message arrived
  • After a reboot the agent runs again

9Many apps, many hosts

  • Use one agent per host or per environment. Each agent has its own settings and its own approvers.
  • Several apps on one host: one agent, one list of sources. Give every source a name after an @, so each incident shows which app it belongs to.
  • A different repository and test command for each app: make the repo map /var/lib/sre-agent/services.json: 
    {"services": [
  {"service": "orders", "repo": "acme/orders", "clone": "/srv/repos/orders", "base_branch": "main", "test_cmd": "npm test -- --ci"},
  {"service": "billing", "repo": "acme/billing", "clone": "/srv/repos/billing", "test_cmd": "pytest -q"}
]}
    A service that is not in the file uses the global settings.
  • Errors from a tool you already use: the agent can read Sentry (sentry:org/project), Datadog (datadog-logs:name, datadog-rum:app-id), New Relic, Application Insights and CloudWatch, or receive errors at POST /ingest/<tool> (signed). Put the keys in the config file and add the source to the log list.
  • Kubernetes: there is no Helm chart yet.

11Upgrade

  1. Finish the open approval cards. Links sent by an older version stop working after the upgrade.
  2. Download the new files and check them (step 3).
  3. Install the new file the same way as before. Settings and data are kept. The database is backed up to /var/lib/sre-agent/backups/ first. A running service restarts by itself. 
    sudo apt install ./sre-agent_NEW-1_amd64.deb         # Ubuntu / Debian
sudo dnf upgrade ./sre-agent-NEW-1.x86_64.rpm         # RHEL family
sudo ./install.sh                                    # tarball, run in the new folder
  4. Docker: load the new image, set the new SRE_AGENT_VERSION in .env, run docker compose up -d.
  5. Check: sre-agent version and sudo sre-agent doctor.

Roll back: sudo apt install --allow-downgrades ./sre-agent_OLD-1_amd64.deb. If needed, stop the service and copy the wanted file from /var/lib/sre-agent/backups/.

There is no apt or dnf repository yet. Download each new version from the release page.

12Remove

sudo apt remove sre-agent        # keeps settings and data   (RHEL: sudo dnf remove sre-agent)
sudo apt purge sre-agent         # also deletes settings, logs and the service user
sudo ./install.sh --uninstall    # tarball; add --purge to delete settings and data too
docker compose down              # Docker; add -v to delete the data volume

Get help: send the output of sudo sre-agent doctor and the last 100 lines of /var/log/sre-agent/sre.log. The agent masks tokens in its log, but read it before you send it.

Optional: link a console

If you have a hosted console project, you can set the keys there instead of using the setup questions. Make a project, set the values, create the agent token, then link the agent. The command saves the link, pulls the settings, trusts the SSH host key (after you confirm it), runs the health check and starts the service:

sudo sre-agent connect --console-url https://YOUR-CONSOLE

Docker: put CONSOLE_URL and CONSOLE_AGENT_TOKEN (starts with sra_) in .env and skip the setup step. Use one way for each agent, setup or console.
